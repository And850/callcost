## Thesis
- CallCost measures the hidden energy and memory cost of a single LLM call on a constrained laptop.
- Priority: 1) on-device energy estimate per call, 2) memory: GiB the model occupies and how much is swapped, 3) latency and money, 4) answer quality (secondary).
- Scope: single calls in a fresh, empty chat. Longer chats cost more energy and memory per call; results are a lower bound for chat use and representative of single-task use.
- Lead finding to report: on a 16 GB Mac, 8-bit and 6-bit swapped on 73.5% / 79.0% of calls (4-bit: 25.5%) and were slower than 4-bit with no quality gain. Whole-machine counters cannot prove inference alone caused the swapping.

## Quality evaluation (new runs)
- Dated amendment: an LLM judge may be primary for runs collected after the amendment, once validated.
- Framework: DeepEval (Apache 2.0). Judge model: Gemini 3.8 Flash; settings and prompt hash fixed before validation; judge calls logged and costed separately.
- Metrics:
  - Maths: exact match (deterministic, no judge).
  - Summaries: G-Eval, one check per existing human-type checklist criterion. Automatic criteria stay deterministic and are not sent to a judge.
  - Summaries: DeepEval Hallucination, validated against the human "faithful" criterion.
  - Not used now: DeepEval Summarization (overlaps), JSON Correctness and agentic metrics (no tasks yet).
- Validation: the 300 human-scored summaries, split by prompt into development and held-out sets before the judge sees any score. Cohen's kappa (unweighted, labels are yes/no) >= 0.6 on held-out. Raw agreement reported as secondary only.
- Self-preference check: kappa reported separately on the cloud answers; below threshold, the cloud row stays human-scored.
- First validation of any metric on a new task type: minimum 30-50 human-labelled items. Afterwards: 5-10% human spot check of every judged run, for every judged metric.
- If kappa < 0.6: summaries are not judge-scored and the app demo runs on maths only.
- Revised validation proposal, owner review 17 October: 1,080 human-type G-Eval checks plus 150 Hallucination evaluations at two requests each = 1,380 physical requests (480 development, 900 held-out). The 930 automatic-criterion G-Eval checks are removed. The hard monetary cap is unset until the owner checks the prepaid balance and explicitly confirms it; no model calls are authorized. See `judge-preregistration.md` for token assumptions, estimates and stopping rules.

## App (truncated version for WAICY)
- Question it answers: which local model should this computer use for this task, given energy and memory cost.
- Local web page (Streamlit or similar). macOS only for the demo; other PCs are the stated next step.
- Flow: read machine (chip, RAM, free memory, swap) -> pick task type (maths or summaries, existing sets) -> pick installed LM Studio models -> probe -> score quality -> recommend.
- Run modes (config): Quick 5 prompts x 2 repeats (labelled "rough"), Standard 10 x 3, Full 30 x 5. Report states the mode.
- Recommendation rule (app defaults, chosen after seeing 17 Oct data; disclosed; user-adjustable):
  - Eligible: quality within X = 5 points of the best local candidate.
  - Choose: lowest median energy per call among eligible.
  - Warning: swap on more than Y = 50% of calls.
  - On 17 Oct data this excludes 3-bit for both tasks.
- AI element: the validated Gemini judge. Optional: Gemini writes a plain-language explanation using only measured numbers.
- Out of scope: Windows/Linux, model downloads, tool use, long contexts, user-defined tasks.
- Known limits: energy needs sudo (powermetrics); probes take minutes, so the demo video uses a sped-up or earlier recording.

### Compatibility and thinking checks to plan before collection

1. Inspect the exact vendor model card, licence, revision, format and runtime requirements, then the installed LM Studio runtime/version and its documented architecture/quantisation support. Check whether it can load the PTQ1_0 GGUF or the MLX 2-bit companion; ordinary GGUF support alone does not establish PTQ1_0 or Bonsai support. Document compatibility as unverified until a separately approved load check succeeds.
2. If LM Studio cannot support either build, assess an adapter for PrismML's OpenAI-compatible llama.cpp server. Plan model selection, fresh single-request chat payloads, streaming/usage parsing, raw evidence capture, process-group memory sampling and error handling. OpenAI-compatible API shape does not prove that the current LM Studio-specific load/unload and measurement hooks work. Record the gap and seek approval before implementation or installation.
3. Check the exact build's chat template and reasoning controls. Prefer thinking off only when supported, and later verify the observed response and token metadata. If thinking cannot be disabled, retain and report thinking tokens separately, count them once in billable output where applicable and disclose the difference from thinking-off Qwen. Missing counts are unavailable with a reason, never zero; do not claim hidden reasoning is off from absent tags alone. Defer this candidate if usable controls or observability are insufficient for an interpretable probe.

### Runtime comparison limits

- A PrismML llama.cpp fork and its PTQ1_0 kernels use a different execution engine from the Qwen MLX runs. Kernel implementation, quantisation scheme, threading, device offload and memory mapping can change energy, swap and latency independently of model quality or parameter count.
- The MLX companion still differs in model architecture, parameter count, conversion and quantisation implementation. Sharing the MLX name does not control runtime versions, kernels or effective settings.
- Future approved probes must record model/file revisions, runtime/fork commit, build options, backend, effective offload/threads, context/cache settings, thinking, output budget, device state and load policy. Match the existing single-call protocol where possible; disclose unmatched settings. Keep load cost separate from request cost and retain sampled-memory coverage and whole-machine energy/swap limits.
- Such measurements compare complete model/runtime configurations for the demo. They cannot attribute an energy/latency difference to ternary weights alone or establish a new within-Qwen knee. Any comparison devised after the initial data is exploratory, not pre-registered.
- Vendor benchmark numbers must never appear as CallCost results, charts or recommendation inputs. Only measurements collected by CallCost in a separately approved probe may be labelled CallCost results. No Bonsai measurements or compatibility claims exist yet.
